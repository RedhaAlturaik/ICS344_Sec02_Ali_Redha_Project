## 1. Overview

This report documents **Lesson 4: Insecure Cloud Configuration** in the Damn Vulnerable Serverless Application (DVSA). The vulnerability is caused by insecure Amazon S3 bucket configuration, where the receipts bucket allows attacker-controlled files to be uploaded into a trusted backend storage location.

The main affected components are:

- Amazon S3 receipts bucket
- AWS Lambda processing function
- IAM permissions
- CloudWatch Logs

The core issue is that the backend assumes files inside the receipts bucket are trusted and legitimate. However, due to weak S3 permissions and insecure bucket settings, a malicious file can be manually uploaded and later processed by backend Lambda logic.

---

## 2. Vulnerability Summary

Normally, only trusted backend services should upload receipt files to the DVSA receipts bucket. In this lesson, the bucket configuration allows an attacker-controlled file to be placed directly inside the backend storage path.

This creates a security risk because Lambda may process the uploaded object automatically, which can lead to:

- backend exceptions
- unsafe file processing
- attacker-controlled input entering trusted workflows
- expanded blast radius through Lambda execution role permissions

Even if full remote code execution does not occur, successful upload and backend processing of an attacker-controlled file proves the insecure cloud configuration.

---

## 3. Root Cause

The vulnerability exists because the S3 receipts bucket is configured too permissively and the backend trusts files that appear in the bucket.

The insecure behavior is caused by:

- disabled or weak public access blocking
- ACLs remaining enabled
- object ownership allowing object writers
- wildcard CORS configuration
- missing strict bucket policy
- lack of file origin validation
- lack of file type and object name validation

The system should not assume that every object in the bucket was generated by a trusted backend function.

### Step 2: Review Bucket Permissions

Inside the bucket, open the **Permissions** tab and review:

- Bucket Policy
- Block Public Access
- Access Control List (ACL)
- Object Ownership
- CORS configuration

Dangerous indicators include:

```json
"Principal": "*"
```

or broad write access such as:

```json
"Action": "s3:PutObject"
```


## 6. Evidence Collected

### Evidence 1: Insecure S3 Bucket Configuration

The DVSA receipts bucket showed insecure configuration indicators, including:

- Block Public Access was disabled
- no strict bucket policy was configured
- object ownership was set to object writer
- ACLs were enabled
- CORS allowed wildcard origins

These settings increase the attack surface and weaken control over who can upload objects into backend storage.

---

### Evidence 2: Successful Malicious File Upload

A malicious test file named `evil.raw` was manually uploaded to the receipts bucket.

Upload path:

```text
s3://dvsa-receipts-bucket-ACCOUNT-ID-us-east-1/2026/04/lesson4/evil.raw
```

The upload completed successfully, proving that attacker-controlled content could be inserted into a trusted backend storage location.

---

### Evidence 3: Lambda Invocation and Backend Exception

CloudWatch logs for the Lambda function showed backend execution and an exception after the upload.

Relevant log group:

```text
/aws/lambda/DVSA-SEND-RECEIPT-EMAIL
```

Observed error:

```text
LAMBDA_WARNING: Unhandled exception
[ERROR] IndexError: list index out of range
```

Although the exact filename did not appear in the logs, the Lambda execution and backend exception confirm that the uploaded object reached the trusted backend workflow.

---

## 7. Security Impact

This vulnerability proves that insecure S3 permissions can bypass the normal application workflow.

An attacker may be able to:

- upload arbitrary files into backend storage
- trigger backend Lambda processing
- cause backend exceptions
- abuse Lambda trust assumptions
- increase impact through over-privileged Lambda roles

The main risk is that a cloud storage misconfiguration becomes an entry point into backend processing.

---

## 8. Fix Strategy

The correct fix is to apply least privilege and harden the S3 bucket configuration.

Recommended mitigations:

- enable **Block all public access**
- remove public or wildcard write permissions
- restrict `s3:PutObject` to trusted backend roles only
- disable unnecessary ACLs
- enforce bucket owner object ownership
- validate uploaded object names
- validate file extensions and content types
- reject unexpected upload paths
- prevent backend code from trusting arbitrary bucket objects

---

## 9. Code and Configuration Changes

### Vulnerable Bucket Policy Example

```json
{
  "Effect": "Allow",
  "Principal": "*",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::bucket/*"
}
```

This is insecure because any principal may upload objects into the bucket.

---

### Secure Bucket Policy Example

```json
{
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::ACCOUNT-ID:role/DVSA-SEND-RECEIPT-EMAIL-role"
  },
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::bucket/*"
}
```

This restricts uploads to the trusted Lambda role only.

---

### S3 Permission Hardening

In Amazon S3:

1. Open the receipts bucket
2. Go to **Permissions**
3. Enable:

```text
Block all public access = ON
```

4. Remove unnecessary ACL-based access
5. Restrict object uploads to trusted backend services

## 10. Verification After Fix

After applying the fix, repeat the same upload attempt:

```bash
aws s3 cp ~/evil.raw s3://YOUR-BUCKET/test.raw
```

Expected result:

```text
AccessDenied
```

This confirms that untrusted users can no longer upload files directly into the receipts bucket.

A valid backend workflow should still be tested afterward to confirm that legitimate receipt generation still works normally.

## 12. Lessons Learned

This lesson shows that cloud configuration is part of application security. Even if the Lambda code is written securely, weak S3 permissions can bypass the application and allow attacker-controlled input to enter trusted backend workflows.

The key lesson is:

```text
Never trust cloud storage blindly.
```

Every AWS resource should follow the **Principle of Least Privilege**, and backend services should validate the origin, type, and structure of every object they process.
